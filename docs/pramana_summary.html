PRAMANA

CodeStar 30 · Technical status report · Verified 29 October 2026 · Local demo

Problem and solution

Brand rules are easy to miss when copy moves quickly from draft to publication. Pramana checks a draft against an approved, versioned rule set and returns evidence a person can inspect before deciding what to do.

Value: every supported warning connects to the exact draft passage, rule version, source excerpt, and suggested next action. A human reviewer owns the decision; the product does not publish content.

Verified user workflow

  1. Creator pastes text or uploads a DOCX with ordinary paragraphs.
  2. System runs four deterministic checks on seeded fictional LumaDesk rules.
  3. Validator checks quotes against the submitted draft and provenance against active rules and sources.
  4. Creator/reviewer inspects the exact draft and Evidence Receipts.
  5. Reviewer records approve, revision, or reject; the same process-local history shows the decision.

Implementation and validation

Connected local application · no LLM or external analysis service

Architecture

Frontend: React, TypeScript, Vite. Backend: Python, FastAPI, Pydantic, python-docx. The request path is intake → deterministic rule engine → finding validator → API response → browser receipt and human decision.

Four seeded checks cover discouraged terminology, one prohibited phrase, one conflicting plan fact, and a narrow required-disclaimer trigger. Candidate evidence is validated before it is returned. The response preserves the exact evaluated draft so receipt passages can be inspected in context.

Review decisions are API-backed (`approved`, `revision`, `rejected`). History shows finding count and appended decisions. It is a shared in-memory demo store, not a durable audit log.

Important limitations

  • No authentication, authorization, organization separation, or rate limiting. Shared history summaries are visible to visitors of the same running instance; a visitor who knows a run ID can change its decision.
  • History retains at most 100 metadata records in process memory and disappears on restart, redeploy, or free-service spin-down. Draft text is not stored in the history repository.
  • Only pasted text and ordinary DOCX paragraphs are supported. No PDF, table/image extraction, OCR, arbitrary claim verification, or automatic rewrite.
  • Do not use with confidential drafts or as a production compliance or audit system.

Three proposed Round 3 improvements

1. Document and image intake

Support one new format at a time with bounded extraction, page/region provenance, confidence indicators, and human confirmation for low-confidence OCR. Estimate: 5–8 days for one format.

2. Visual brand and accessibility

Start with measurable logo, palette, contrast, and missing-alt checks using approved brand assets. Keep subjective judgments with human reviewers. Estimate: 4–7 days.

3. Persistent audit and analytics

Add authentication, organization isolation, retention policy, and relational event storage before durable analytics. Estimate: 8–12 days; includes privacy, backup, and access-control work.

Conclusion: The local demo now supports the central evidence-to-human-decision path and has reproducible build/test results. It is prepared for review, not ready to treat as a secure production service. Full risks and measurable roadmap criteria are in the project docs.
